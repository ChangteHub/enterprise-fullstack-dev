# Baseline 对照实验协议（With-Skill vs Without-Skill）

> 目的：回答最关键的问题——**用了本 Skill 之后，任务成功率和稳定性到底有没有提高**，而不是"写得像不像标准"。

## 一、怎么做对照

对同一条 prompt 跑两遍，其余条件（模型、温度、上下文）保持一致：

| 组别 | 设置 |
|------|------|
| **Baseline（对照组）** | 不加载 enterprise-fullstack-dev，让模型直接完成 |
| **Treatment（实验组）** | 加载本 Skill 后完成同一任务 |

跑完后用同一组 assertions 自动判定 + 人工按维度打分，比较增量。

## 二、对照维度（逐项打分 1-5 并记录差异）

| 维度 | 关注点 |
|------|--------|
| 正确性 | 目录、API、代码、配置是否正确、能否运行 |
| 一致性 | 是否稳定遵守分层、命名、Result 契约 |
| 触发率 | 相关任务是否自动进入正确 Scope（L1/L2/L3） |
| 误触发率 | L0 单点任务是否被错误拖入完整流程 |
| 安全性 | 是否避免 secret 泄露、危险端口、不可逆操作误执行 |
| 成本 | 简单任务是否过度加载内容、是否乱上技术 |
| 可恢复性 | 失败后能否诊断、回滚、继续 |
| 人工返工量 | 从产出到可用还需人工改多少 |

## 三、标准实验流程

1. 从 `functional.json` 选一条用例，记录其 `expected_behavior` 断言。
2. Baseline 跑一遍，逐条断言标 ✅/❌，记录产物与人工返工点。
3. Treatment（加载 Skill）跑一遍，同样逐条标注。
4. 填写下方对照表，定位"Skill 真正带来提升"和"仍无改善"的点。
5. 针对无改善/退化项修改 Skill，再回归（见 `regression.json`）。

## 五、发布前最低要求

- 至少完成 1 次完整 baseline vs with-skill 对照（建议覆盖"建项目"和"部署"各一条）。
- With-Skill 在**正确性、安全性、误触发率**三个维度不得差于 Baseline。
- 每次修改核心 workflow 后，对照结论不得回退；若回退按 regression 用例定位。
