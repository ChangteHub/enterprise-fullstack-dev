# 模块化单体架构（Modular Monolith）

> **Pre-Check（加载前确认）：** 单体已出现边界混乱（service 互相随意调用、事务跨模块）？团队 >5 人并按业务域分工？有独立部署/扩展需求的模块吗？——若三项都不成立，留在 Mode A 简单单体即可，不要提前升级。
>
> 本文件代码均为参考模板（Reference Template），可结合实际业务调整实现，但须保证可编译运行、不引入 bug；不确定时遵循模板。
>
> **Deliverable（读完必须产出）：** 模块边界定义 + 模块间通信约束 + 演进触发条件。

## 定位：单体与微服务之间的中间态

```
简单单体（Mode A）         模块化单体                微服务（Mode B）
一个 Spring Boot 工程  →   一个工程，内部按业务域   →   多个独立工程/进程，
按技术分层(controller/      分模块(module)，层内      独立部署、独立数据库
service/ repository)        再分层，模块间有契约
```

**选择信号**：模块间开始出现"我知道你的内部实现"的调用、单模块改动牵连整个工程回归、某模块资源需求与其他模块显著不同（如报表模块吃内存）。只满足一条 → 先用包结构约束；满足两条以上 → 考虑 Maven 多模块。

## Maven 多模块结构

```
backend/
├── pom.xml                      # 父 POM：统一依赖版本
├── app/                         # 唯一可运行入口（打包成 fat jar）
│   └── src/main/java/.../AppApplication.java
├── module-product/              # 商品模块
│   └── src/main/java/.../product/
│       ├── api/                 # 对外契约（DTO + 接口），其他模块只能 import 这里
│       ├── internal/            # 内部实现（controller/service/repository）
│       └── config/
├── module-order/                # 订单模块（结构同上）
└── module-shared/               # 公共内核：Result/PageResult/异常基建/工具
```

**硬规则（模块间边界）**：
1. 模块间只允许依赖对方的 `api/` 包，禁止 import `internal/`（用 Maven enforcer 或 ArchUnit 在 CI 里强制，不靠自觉）
2. 模块间调用走本地接口（进程内），**不假设共享事务**——跨模块写操作在调用方组织补偿/最终一致，不为"规范"传播 `@Transactional`
3. 数据库表按模块划归属：每个表只有一个 owner 模块，其他模块只能通过 owner 的 api 读写，禁止跨模块 JOIN 业务表（视图/宽表除外，需注明）
4. `module-shared` 只放无业务语义的基建，放业务类就是边界腐烂的开始

## 对比决策

| 维度 | 简单单体 | 模块化单体 | 微服务 |
|------|---------|-----------|--------|
| 部署单位 | 1 个 | 仍 1 个 | N 个 |
| 事务 | 本地事务 | 本地事务+边界约束 | 分布式（Saga/最终一致） |
| 团队规模 | 1-5 人 | 5-15 人 | 15+ / 平台团队 |
| 引入成本 | 低 | 中（多模块构建+边界测试） | 高（网关/注册/链路/运维） |
| 回退难度 | — | 容易（合并回单模块） | 高 |

**不要为了"架构好看"引入模块化单体**：它解决的问题（边界混乱、并行开发冲突）必须真实发生。包结构清晰的单体可以撑到很远；边界规则被破坏时先靠 Code Review 和 ArchUnit 治理，其次才升级多模块。

## 演进触发条件（满足才动）

1. CI 时长因单模块构建明显拖慢（>15min 且无法用缓存/并行解决）
2. 两个及以上团队在同一工程产生频繁合并冲突
3. 某模块需要独立扩缩容或独立技术栈（如报表模块换列存）
4. 模块间边界已被 api/ 约束良好运行超过一个迭代周期（先有边界纪律，再有物理拆分）
