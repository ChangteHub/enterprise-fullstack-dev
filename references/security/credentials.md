# Credential Lifecycle Policy（凭据生命周期）

> **Pre-Check（加载前确认）：** 涉及生产部署或管理员/密钥类凭据的生成与交付了吗？项目是否存在"随机生成只打印一次"的初始化逻辑？（audit 时应主动检查）
>
> 本文件为策略参考模板（Reference Template）：生命周期阶段与各级环境要求是规范，具体实现随项目栈调整。
>
> **Deliverable（读完必须产出）：** 本项目凭据的六阶段对照表（生成/交付/首用/恢复/轮换/审计），缺失阶段列入 Gap。

## 为什么需要它

实践中最典型的阻碍：管理员密码随机生成 → 只打印一次日志 → 容器重建日志丢失 → **无恢复路径** → 测试阶段被迫用 SQL 直插数据库绕过应用层。根因是规则只覆盖了"生成"，没有覆盖完整生命周期。

## 完整生命周期（六阶段）

```
生成 → 受控交付 → 首次使用 → 轮换 → 丢失恢复 → 撤销 → 审计
```

| 阶段 | 开发/测试环境 | 生产环境 |
|------|--------------|---------|
| 生成 | 可由 seed 脚本生成已知测试凭据 | 随机生成，禁止硬编码 |
| 交付 | **seed 脚本显式创建测试账号**（入 Git 可评审） | 受控注入（env/secret manager），**禁止一次性日志打印作为唯一交付** |
| 首次使用 | 直接使用测试凭据 | 建议强制首次登录修改密码 |
| 恢复 | `reset-test-data.sh` 或开发辅助脚本 | **必须存在**正式的管理员重置路径（脚本/流程），没有 = P0 缺口 |
| 轮换 | 脚本可重建凭据 | 支持密钥/密码轮换（改 env 重启即可） |
| 审计 | 记录测试操作 | 管理操作入审计日志（如 admin_log 表） |

## 审计检查项（project audit 应主动检查）

- [ ] 代码中是否存在"随机生成 + 只打印一次"且**无恢复路径**的管理员初始化逻辑？
- [ ] 初始凭据是否可通过受控方式重新交付（env 注入 / 重置脚本）？
- [ ] 生产是否强制首登改密？
- [ ] 密钥类（JWT secret/DB 密码）是否全部支持 env 注入轮换？

## 测试凭据规范

- 测试账号**只能**来自 `scripts/seed-test-data.sh`（入 Git、幂等、可评审）
- 禁止 ad-hoc SQL 直插用户表——即使开发环境允许手工 SQL，也不得作为 Skill 默认操作路径
- 测试密码标注 `Test only` 语义（如 `SmokeAdmin2026!`），与生产凭据严格隔离
